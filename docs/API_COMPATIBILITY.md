# API compatibility matrix

All target business APIs below are **planned, not implemented**. Only GET /actuator/health exists publicly in backend-next. Current frontend remains on backend port 8088; replacement is 8089. Both use /api/v1 as their intended business prefix, with incompatible contracts.

Evidence: docs/openapi.json; backend feature controllers and dto/request records; frontend/src/shared/api/client.js; inspected frontend feature pages/components. Consumer paths below are relative to frontend/src; abbreviated components/pages paths inherit the preceding feature. Dynamic calls were resolved using Fleet.kind (buses/stops/routes/staff) and Operations.prefix (admin/counter/driver), not just literal-string matching.

## Cross-cutting changes

| Aspect | Current | Target |
|---|---|---|
| Authentication | Session cookie, CSRF fetched before mutation; refresh CSRF after login/logout | JWT + persisted refresh lifecycle; browser token transport not yet implemented |
| IDs | UUID strings | BIGINT identifiers; frontend number/string serialization must be settled with implemented DTOs before cutover |
| Money | fareMinor/amountMinor integer minor units, currency | BigDecimal/NUMERIC(12,2); never trust client totals |
| Roles | Single PASSENGER/ADMIN/DRIVER/COUNTER_STAFF | UserRole collection: PASSENGER/ADMIN/MANAGER/COUNTER_STAFF |
| Booking | Separate hold then confirmed booking, optionally unpaid | Pending booking/allocation then payment-before-confirmation |
| Errors | message + fieldErrors consumed by fetch helper | Six-field timestamp/status/code/message/path/traceId; field-level UX must adapt to implemented validation contract |
| Status codes | Current codes recorded per operation below | Foundation 400/401/403/404/405/500 error mapping; target business success/conflict codes finalized per increment, not invented here |
| CORS | Existing exact origins/session semantics | Denied during foundation; explicit origins and refresh/CSRF rules required before browser integration |

## Target-only interfaces

The specification also introduces refresh, change-password, station/route details, separate seat-layout CRUD, independent driver management, trip driver assignments and fares, segment-aware availability, payment attempts/webhooks, per-passenger tickets, counter ticket verification/check-in and partial passenger cancellation. Implement and document each in its own increment before frontend use.

## Unresolved target details (future feature tasks)

The source endpoint lists do not fully define staff creation, management trip listing, passenger trip detail, manifests, password recovery, exact refresh transport, every response DTO or success status. Those are recorded gaps, not permission to invent endpoints during foundation work. The relevant future increment must resolve them before public API publication and frontend cutover.

The React blueprint remains deferred. No Axios, TypeScript, routing, query-cache or token-storage change is made to the working frontend here.
